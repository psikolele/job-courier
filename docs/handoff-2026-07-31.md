## 1. Il problema iniziale — regressione silenziosa, non un bug visibile nei log

Segnalazione utente: cambiando lingua sul sito, molte parti restavano in italiano. Diagnosi: cross-check programmatico fra le chiavi definite nei 4 file `src/locales/*.json` e quelle effettivamente chiamate con `t()` nel codice.

**Causa:** i commit che riversavano il copy dai DOCX del cliente (`7c71136`, `a6b0af6`, `8151e94`) avevano sostituito le chiamate `t()` con testo italiano letterale. i18next non segnala nulla in questo caso — la chiave semplicemente non viene più chiamata, nessun errore in console. In italiano il sito sembrava corretto; solo EN/DE/FR mostravano il buco.

**Scoperta strutturale:** nel codice convivono **tre pattern i18n diversi** — `t()` + locale JSON, oggetti inline `{label, labelEn, labelDe, labelFr}`, e ternari `isIt ? ... : isDe ? ...` in `getLocalizedData(lang)`. Una stringa italiana letterale nel JSX non si distingue a colpo d'occhio da una tradotta: è la causa strutturale per cui la regressione è passata inosservata per giorni.

**Fix (29/07):** Hero e ComeFunziona riagganciati a `t()`, `come_funziona.*` riscritto in 4 lingue sul copy DOCX attuale (prima EN/DE/FR avevano il copy *vecchio*, pre-revisione), 8 chiavi `blog.*` mancanti aggiunte. Locale: 119 chiavi con buchi → 140 in parità.

## 3. i18n sistematico — due sessioni, metodo a scala

Il problema vero non era solo il bug puntuale: la traduzione del sito non era mai stata completata. Misura prima di agire: **51 token di codice letti per ogni token di testo effettivamente da tradurre** (226k char di sorgenti contro 4.4k char di stringhe IT nei primi 4 file). Leggere ogni file per intero e editarlo a mano avrebbe sforato il budget di sessione di 2-3×.

**Metodo adottato:** script Node one-shot, non agenti, non letture di file interi.

1. **Estrattore** (`i18n-extract.cjs` → poi `i18n-census.cjs` v2) — trova le stringhe IT senza che io legga i sorgenti: nodi di testo JSX, testo interpolato, attributi, proprietà di oggetti JS. Segnala i literal con occorrenze multiple come "ambigui" invece di sostituirli alla cieca.
2. **Applier guardato** — ogni sostituzione dichiara quante volte *deve* colpire il file. Se il conteggio non torna, il file **non viene scritto**, nessuna riscrittura parziale. Ha rifiutato 10 file su 24 al primo giro nelle due sessioni, ogni volta per una ragione reale: `Sede:`/`Settore:`/`Ruolo:` compaiono 2 volte (card lista + dettaglio), `Candidati` è anche dentro il nome del componente `PercheCandidatiWidget`, `Dettagli` è prefisso di `Dettagli posizione`, `Torna alle aziende` compare 3 volte legittimamente (stati loading/error/notfound).
3. **Locale via script**, mai a mano — un file Node scrive le 4 lingue in un colpo, poi uno script di verifica conferma parità di chiavi fra tutte le lingue prima del build.
4. **Build + lint con confronto pre/post** — non "zero errori" (il progetto ne ha già 13 pre-esistenti), ma **stesso numero di prima**, file per file, per garantire zero regressioni introdotte.
5. **Verifica live** con `i18n.t()` diretto via `javascript_tool`, non lettura del DOM renderizzato — il DOM ha dato 3 falsi negativi in questa sessione (CSS `text-transform` maiuscolo che nasconde il case reale, tab dirottato su porta morta della preview, click su una card che rimonta il componente). Leggere il valore risolto dalla libreria i18next elimina la categoria di errore.

**Risultato sessione 1** (offerte, dettaglio offerta, footer, filters + fix lingua sui 13 link jobroom): locale 171→214 chiavi. Deploy `7a9z49l1d`.

**Risultato sessione 2** (footer colonne, modal login navbar, 12 componenti, FAQ struttura, 404): locale 214→300 chiavi. Un bug introdotto e trovato prima del merge — Footer toccato in entrambe le sessioni, l'applier non controllava se l'hook `useTranslation` esisteva già → dichiarazione doppia di `const { t }`, build rotta. Trovato dal build stesso (non serviva altro), corretto, riverificato lint 13=13 con HEAD.

**Correzione di un mio errore, non del codice:** il censimento segnalava `blogIndex.js` come bug (titoli sempre italiani). Falso positivo — il file ha già array `IT/EN/DE/FR` separati ed esportati correttamente; il mio euristico di rilevamento italiano matchava parole del dominio job ("Candidates") anche in testo inglese legittimo. Verificato leggendo il file prima di "fixare" un non-problema.
